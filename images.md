# Photography and loading specification

## Authoring and delivery folders

Keep client originals in the top-level `assets/` folder. Use this convention:

| Location | Content |
| --- | --- |
| `assets/photos/<project-slug>/originals/` | Unmodified camera or photographer source files |
| `assets/photos/about/originals/` | Approved portrait or studio/garden detail |
| `assets/photo-manifest.json` | Source inventory, ids, roles, approvals, crops |
| `assets/brand/` | Supplied identity files and presentation board |
| `public/assets/images/` | Generated web derivatives only |
| `src/generated/image-manifest.json` | Public derivative metadata generated by tooling |

For the current preview, the 26 Snowbird after photographs are organized beneath `assets/photos/<project-slug>/originals/`, and the nine client-supplied before photographs remain beneath `assets/updatedBefore/`. `assets/starter/` and `assets/raw/` are intentionally excluded from the manifest and build. All source folders remain authoring-only.

Do not copy `assets/` wholesale into `public/` or `dist/`. The brand presentation board and original photo metadata are handoff materials, not website payloads. Select only the required production logo/favicons when copying brand files.

Source names should be lowercase, descriptive, and stable, for example `canyon-retreat-after-01.jpg` and `canyon-retreat-before-01.jpeg`. Keep ids stable even if a file is renamed.

Use JPEG/PNG/TIFF source exports supported by the chosen pipeline. If the client supplies HEIC or RAW files unsupported by that environment, preserve them and request/export a high-quality supported working copy; do not rename the extension and claim conversion.

## Source manifest contract

Copy [assets/photo-manifest.example.json](assets/photo-manifest.example.json) to `assets/photo-manifest.json` when implementing and fill it with real photo records. Its null paths intentionally reference no missing files.

Each photo record has:

- `id`: unique stable id, used in the project data.
- `projectId`: matching project id, or null for the About image.
- `role`: `before`, `after`, `detail`, or `about`.
- `source`: path relative to the repository root, or null while missing.
- `alt` and `caption`: descriptions written after inspecting the photo; null until known.
- `approved`: boolean, false until permission and correct usage are confirmed.
- `credit`: required public attribution text or null.
- `focalPoint`: normalized `{x, y}` values from 0 to 1, default `{x: 0.5, y: 0.5}`.
- `crops`: explicit optional named crop recipes, initially empty. Each approved recipe states aspect ratio, focal point, and intended use.

Maintain any private consent notes separately from public data. Only approved attribution and presentation fields belong in the browser manifest.

## Build-time image processing

`scripts/prepare-images.mjs` implements this pipeline in JavaScript with Sharp.

1. Validate manifest ids, source paths, roles, approval flags, and project relationships. Reject paths escaping the source asset directory.
2. In preview, skip null source records and record a placeholder state. In publish mode, require all images referenced by published content to be approved and present, with an inspected nonempty descriptive alt field for informative project photography. Unreferenced draft slots need not fail a publish build.
3. Preserve originals. Apply orientation and normalize derivatives for web display; remove EXIF/GPS and other unneeded source metadata. Confirm resulting color and orientation visually.
4. Produce AVIF, WebP, and JPEG fallback derivatives. Initial quality settings may be approximately AVIF 50, WebP 78, and JPEG 82; tune them against the real photo's fine foliage and tonal detail.
5. Use candidate widths of 480, 768, 960, 1280, 1600, 1920, and 2560px as appropriate to the source and use. Do not upscale. Omit duplicate output sizes and record actual dimensions, particularly when a small source caps the result. Sharp provides `withoutEnlargement` for this purpose. [Sharp resizing](https://sharp.pixelplumbing.com/api-resize/)
6. Keep a natural-aspect-ratio family for full photographs. Generate separate crop families only when the art direction needs them: typically 16:9 wide hero, 4:5 mobile hero, and 4:3 project thumbnail. Do not generate every family for every photo automatically.
7. Never crop a before/after pair into apparent alignment without verifying the two views and documenting the crop. Use natural ratio figures when views differ.
8. Add a content hash incorporating source bytes and transformation settings to each filename. Regeneration should reuse unchanged outputs and remove stale files only inside the generated destination.
9. Write the public manifest with variant id, format, URL, actual width/height, bytes, alt/caption/credit, and background placeholder color. Do not expose source paths or private approval notes.
10. Validate referenced outputs, nonempty files, reported dimensions, srcset widths, and selected-image byte budgets. Print a concise summary for the implementation record.

The first run with no photos should create a valid empty public manifest for preview mode. Do not make the future developer debug broken file imports before any photos exist.

## Responsive rendering contract

`ResponsiveImage` receives an image id, intended crop family, `sizes`, CSS aspect ratio, and priority intent. Render one `<picture>` with AVIF and WebP `<source>` elements and one JPEG fallback `<img>`. Width descriptors must equal real output widths. Give the fallback intrinsic `width` and `height` and reserve the chosen frame before loading. `<picture>` supports format alternatives and crop changes by media condition; `sizes` describes the rendered slot width. [MDN picture element](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/picture)

For art direction, declare the mobile format sources before desktop/default sources and include an appropriate mobile JPEG source if using a different crop. Specify source dimensions or breakpoint-specific wrapper aspect ratios so the browser reserves the correct space before selecting a crop.

For the full-width hero under the container/gutter system in design.md, the initial `sizes` expression is:

```text
(min-width: 1568px) 1440px,
(min-width: 1440px) calc(100vw - 128px),
(min-width: 1024px) calc(100vw - 96px),
(min-width: 640px) calc(100vw - 64px),
calc(100vw - 40px)
```

Derive project-grid slot sizes separately from their actual column span and gaps. Do not reuse `100vw` for a small desktop card. At high device pixel ratios the browser may pick a larger candidate; inspect `currentSrc` and transfer size at the tested mobile DPR.

Use `object-fit: cover` only inside an intentionally cropped frame. Apply per-photo object position from the approved focal point. Natural project photographs may use `height: auto` instead. Never stretch a photo to fit.

## Loading policy

| Image | Policy |
| --- | --- |
| Homepage featured after | Eager load, React `fetchPriority="high"`, never lazy |
| Directly opened project hero | Eager load and high priority for that route |
| Other initially visible photos | Eager where visibly necessary, normal priority |
| Below-fold project images | Native lazy loading, normal/low priority |
| Optional comparison after interaction | Fetch only when needed; preserve layout |
| Unopened project galleries | Do not preload or mount hidden images |

`loading="eager"` prevents lazy deferral; `fetchPriority="high"` supplies a scheduling hint. Do not mark every image high priority. [web.dev fetch priority](https://web.dev/articles/fetch-priority)

On initial entry, make the hero discoverable in the initial HTML. For the early SPA preview, emit a responsive preload for the known home hero when needed. For publish mode, prerender the route-specific hero picture and add a matching preload only if measurement shows a benefit. All preload URLs, crop media queries, and `imagesizes` must match the rendered asset selection. Prefer preloading one supported preferred format; do not preload AVIF, WebP, and JPEG simultaneously. Inspect the network to confirm no unnecessary duplicate downloads. [Responsive image preload guidance](https://web.dev/articles/preload-responsive-images)

No CSS background for the content hero, base64 full-photo embedding, autoplay video hero, JavaScript lazy-loading library, gallery-wide prefetching, or device-hidden duplicate hero image.

Loading/error backgrounds use `--color-surface`; no spinning logo or shimmering skeleton. If an actual image fails, preserve its frame and replace it with concise “Photo unavailable” text. Never leave an endless loader or recursively retry the same broken fallback.

## Project performance budgets

These are acceptance targets chosen for this site, not guarantees or external standards. Measure a cold-cache production build with real assets.

| Item | Target |
| --- | --- |
| Selected phone hero derivative | At most 250KB transferred in AVIF/WebP at tested DPR |
| Selected desktop hero derivative | At most 550KB transferred in AVIF/WebP |
| Typical selected grid image | At most 150KB on phones; at most 250KB desktop |
| Route hero JPEG fallback | Aim below 700KB; verify visual quality and record exceptions |
| Initial JavaScript | At most 150KB gzip |
| Initial CSS | At most 30KB gzip |
| Initially loaded fonts | At most 120KB WOFF2 total; `font-display: swap` |
| Cold mobile transfer through LCP | At most 1MB, including HTML/CSS/JS/fonts/visible imagery |

Do not solve a byte overrun by making the garden visibly muddy. Adjust crop dimensions, candidate sizes, quality, and unnecessary requests first; record a reasoned exception if real foliage needs more detail. A small source cannot become a sharp full-screen hero through upscaling. Ask for a better original while retaining an honest preview.

Target good Core Web Vitals at the 75th percentile after sufficient real-user data exists: LCP at most 2.5 seconds, INP at most 200ms, CLS at most 0.1. Before launch use lab measurements as a diagnostic and local interaction checks as a proxy; do not claim field INP from a Lighthouse navigation audit. [Core Web Vitals definitions](https://web.dev/articles/vitals)
